Draconis · systems tour

How the system works.

A rack of GPUs at home, a crowd of small machines, and a pile of software I built so they do useful work without me hovering. This is the tour: what each system does, how work flows through it, what is actually running, and what still isn’t. I’m a tester at heart, so the rough edges are on the page too.

01 · Foundation

The fleet running

Local GPUs do the thinking. Small machines do the legwork. The cloud catches what neither can. Every call gets counted.

llm proxiesSwitchboard (FastAPI + SQLite)Dockerper-GPU telemetry

I run my own inference, in two tiers. The backbone is a few big machines: a six-GPU CUDA server that runs a model per card plus images, video and speech; a six-card accelerator box with its own model on each card; and a Mac with 256 GB of unified memory that holds the one model too big for anything else. They are busy on purpose, so I don’t treat them as on call for everyone. The edge is a crowd of smaller machines with mid-size GPUs, plus the agent nodes that do the day-to-day work: routing, classifying, embedding, summarising, running coding agents. Bulk and utility work goes to the edge so the backbone stays free for what it’s there for.

Every serving box runs its own proxy. There is no single router for the whole fleet, and that’s deliberate: the right route depends on the job. Each proxy has its own fallbacks. It tries local hardware first and falls back to a hosted provider when it has to. Nothing calls a model directly, because a call that skips the proxy never shows up in the books.

Switchboard is the books. It polls every proxy and records which machine, which model and which job made each call, how long it took, and whether it worked. I can switch a provider off for one box or for the whole fleet from the same page. Next to it sit a few other windows: per-GPU telemetry, a pixel-art office where every live agent session is a little character at a desk, and a directory page that ties the dashboards together.

Reckoner watches the plans. Every AI subscription and prepaid balance I use has its own limits: a five-hour window, a weekly cap, a monthly allowance. Reckoner reads each vendor's usage once, in one place, and hands those limits to Switchboard, so a proxy stops routing work to a plan before it runs dry instead of finding out from an error.

What works

  • A proxy on every serving box, with fallbacks that depend on the job
  • Usage attribution per machine, model and caller, plus provider switches for one box or the whole fleet
  • Edge nodes with mid-size GPUs serving agent traffic
  • A public, interactive map of every box and model (linked below)

What doesn’t yet

  • Each proxy is its own copy of the same code, so a change has to be deployed box by box and then verified. Drift between copies is the recurring bug.
  • Two more edge tiers are on the plan, a faster one for hard steps and a low-power one for embeddings. Neither is online yet.
  • Power is a real limit. Loading several GPUs at once tripped the UPS one afternoon, so heavy jobs are now sequenced.

02 · Shared brain

Fleet Memory running

Agents forget. This is the part that doesn’t.

sqlite-vecSQLite FTS5sentence-transformer embeddingsREST + MCP bridge

Two failures drove it. One: an agent answers a question about my own setup from a stale guess instead of checking. Two: a decision made mid-session dies when the context window compacts. So there is one place agents look things up and one place they write things down.

There are two stores. Facts and decisions live in a semantic store: short notes, each tagged with how I know it. human-said means I stated it, observed means a tool showed it, agent-thought means the agent inferred it. That distinction matters, because an inference should never carry the weight of something I decided. Conversations live in a full-text archive of thousands of past sessions. Search spans both, so a hit can be the fact and the conversation it came from.

The vector side works like this. When a fact is saved, a small sentence-transformer model turns the note into a vector of 384 numbers, and that vector is stored beside the text in a SQLite database with the sqlite-vec extension. A question gets embedded the same way and matched by cosine similarity, so it can find a note even when the words differ. One catch: a vector search always hands back its nearest neighbours, even for gibberish. So the lookup tool throws away anything under a relevance floor and says “nothing on record” instead of showing a weak match. The conversation archive is the keyword side: SQLite FTS5 over the transcripts, exact words and terms, with no embeddings yet. One query goes to both stores and the results are merged, with facts ranked ahead of conversation hits on ties. The vectors give the meaning, and the keywords catch the exact strings: a model name, an error message, a hostname. The test tooling keeps a separate vector store of its own (ChromaDB, for proven test steps), described in its section.

Agents get two deliberate tools, recall and remember, plus a hook that injects memory automatically, but only when a prompt actually points backwards: “last night”, “remember when”, a project by name. A plain task pulls nothing. For fleet work there is a gate on top: an agent’s tool calls are blocked until it has recalled what we already know. A batch job also mines old transcripts for decisions and writes them back as facts, so durable knowledge doesn’t depend on any one agent remembering to save it. A small app, Mnemo, shows what is stored, where it came from and who is asking.

What works

  • Facts store and conversation archive, searched together
  • Provenance on every fact, written at the moment it is saved
  • Cue-gated retrieval with a hard size ceiling, so memory never floods the context
  • Chat-export ingest from other assistants, and caller analytics in Mnemo

What doesn’t yet

  • It only knows what got written down. Facts mined by the batch job are tagged as such, so they never pose as things I actually decided.
  • If the conversation archive is unreachable, search quietly returns facts only. That is a known gotcha, not yet a loud failure.
  • Memory is not a substitute for checking live state. When the two disagree, live state wins, but the agent has to have looked at memory first.

03 · Reading pipeline

Content intake running

A dozen kinds of source go in. A scored, readable queue and a funnel of ideas come out.

n8nPythonMarkdown + frontmattergitlocal + hosted LLMsfull-text + vector search index

I read a lot: articles, posts, newsletters, forums, videos, podcasts, books, new repos. I don’t want to find it all by hand, and I don’t want a feed deciding what matters. So every source gets its own downloader that pulls new items on a schedule and writes each one as a Markdown file with frontmatter into a repo for that media type. Hundreds of thousands of items live there now.

The Librarian is the single chokepoint. Every item goes through one scoring workflow: an LLM rates it against my interest profile and pulls out the substance, meaning the ideas, the lessons and why it matters to me. Everything downstream reads scored items, never raw scrapes. The plumbing between the sources and the Librarian is a self-hosted n8n: workflows poll the RSS feeds, forums, saved posts and video channels, hand each new item to the scoring workflow, and file the result. The scorer itself is an n8n workflow, so one place decides what an item is and where it goes, and a fix there fixes every source at once. What passes lands in a reading queue, the Workshop, where I triage, drill into any source, or paste a URL and have it fetched, scored and filed on the spot.

Downstream of the Librarian sits a search index with both halves: full-text and vectors. Articles, video and podcast transcripts, forum posts and news are cut into chunks and embedded. Today that is roughly 580,000 documents and 3.3 million chunks, tens of gigabytes of SQLite files on one edge box. It answers “what have I read about this”, where Fleet Memory answers “what did we decide”, and an agent can search it by meaning or by exact words. Fleet Dispatch keeps a smaller index of its own for news articles. The Ladder’s grounding gate uses embeddings too: it searches fleet memory for what is already settled before an idea reaches me.

The Ladder is where the good ones go to work. A source sparks an idea, an idea becomes a testable hypothesis, a hypothesis becomes an experiment, and an experiment that holds up becomes a proven method. Results loop back in as new sources. In front of it sits a grounding gate: a local model that throws out ideas I have already tested and settled before they reach me.

What works

  • A downloader for every source, one repo per media type
  • One scoring chokepoint that also extracts the substance
  • The Ladder running in a container, with the grounding gate in front of it
  • An absence monitor on every source

What doesn’t yet

  • Every scraper has died silently at least once. One sat dead for thirteen days while its wrapper exited clean. So I stopped trusting success codes: the monitor alerts on how long since a source last imported anything, not on whether a process is alive.
  • Paywalled and link-only items give you a headline and not much else. The rule is never to score a stub: fetch the real body, or mark the item unscored. Closing that gap for every source is still work in progress.
  • The Ladder draws on the same scored input as the Librarian, so left alone it remixes content into generic mush. The grounding gate helps. It doesn’t make ideas good by itself.

04 · Daily briefing

Fleet Dispatch running

The news, once a day, without the feed: a web page, an email and a spoken edition, all built from one ranked list.

Python static buildsmall local classifierLLM editorial passestext-to-speechemail

Dozens of news feeds are scraped every half hour and sorted into sections by a small local model. Stories about the same event are clustered into one, and the ranking is simple on purpose: how many outlets covered it, weighted by how fresh it is.

Each morning a static page is built: an index, a page per section, an archive. The email is rendered from the same ranked list, so the lead story matches the page and every item deep-links to it. On top of that, LLM passes add the editorial layer: five things to know today, a one-line why-it-matters on the top stories, and a spoken digest of roughly fifteen minutes that a text-to-speech voice reads, with a player embedded in the page.

What works

  • Page, email and audio edition built from one ranked list
  • Editorial passes: five things to know, why it matters, a spoken digest
  • Section pages and an archive of past editions

What doesn’t yet

  • It has to go out every day, and that is the whole job. It has not always: when the machine under it dropped off the network for several days, so did the edition. That is the case for self-healing operations (section 10), not for more features.
  • Room is reserved for a daily puzzle and comics. Neither exists yet.
  • Production is meant to move into Podcast Studio. For now the Studio only mirrors each day’s edition.

05 · Audio

Podcast & voice studio running

A production line for audio shows: write it, voice it, check it, ship it. Voices are made somewhere else, on purpose.

FastAPIReactWhispermulti-speaker TTS enginesffmpeg

Podcast Studio is the production side. Work is organised as networks, shows, seasons and episodes, and each show has its own format and cast: about forty formats so far, from roundtable debates to single-voice explainers. A scheduler fires each show on its own schedule in its own timezone, picks the topic, and walks the episode through the phases: research, script, validation, voice, check, post, publish. Any phase can be regenerated on its own.

The phase I care about as a tester is the check. After the voice render, a speech-to-text model transcribes the finished audio, the transcript is diffed against the script, and speaker count and identity are checked. A bad take goes back for regeneration instead of out the door.

Voice Forge is a separate tool, and the split is the point. The Studio uses voices from a shared pool but doesn’t make them. Forge creates and remixes voices and has one hard rule: never a recognizable real person. Every voice is derived to be distinct and measured for it. Voice engines are pluggable per show, so a show can use a fast preset voice or a slower, higher-quality cloned one. The Dispatch’s spoken edition uses the same stack.

What works

  • Studio and Forge both live, as separate services
  • Scheduled shows that produce on their own
  • A full end-to-end delivery, research to published audio, proven
  • The format catalog restores itself on every boot

What doesn’t yet

  • For a long stretch, episodes silently didn’t deliver. Three pieces of glue each worked out where the script file lived, two with stale paths, and the failure looked green. The fix was a design rule: stages hand files down directories, and the directory is the contract.
  • Mastering is meant to be its own service. It isn’t built.
  • Delivery reliability is still the soft spot.

06 · Software factory

Karakuri in progress

A factory made of small, cheap, local models that tries to behave like one big frontier model, with gates so it doesn’t ship slop.

GoNATS busrootless Dockerlocal open-weights modelsper-service proxies

A frontier model works because one context holds everything. Karakuri’s bet is that many small local models can get close if two things are true. First, all the data is available to all the agents all the time. That means access, not injection: push what is relevant, let agents look up the rest, because too much context overwhelms a small model. Second, no slop: the quality gates don’t get lowered to make a run pass. When a gate fails I fix the gap behind it, not the gate.

A request becomes a story, and a story moves through a state machine on a message bus. Every hand-off is an event, and no service calls another directly. A PM agent writes acceptance criteria, researching unfamiliar mechanisms first instead of guessing. An architect designs. QA reviews the design and plans tests before any code exists. The coder builds in any language: there is no stack whitelist, so the coder declares the install, build, test and run commands in a manifest. Then the work is checked against the design, tested, and put through a security panel and a QA panel in parallel, and an SRE pass checks it can be deployed. Docs get written. The shipper opens a scored pull request. The agent that tests the code is not the one that reviewed the design.

When a story stalls, a supervisor, a stronger model, reads the situation and returns a structured directive: let a hollow objection through, fix the acceptance criteria, instruct a specific agent, or fail the story. The point is that I’m not the one unsticking it. Karakuri lives on its own isolated container runtime at low priority with nothing reserved for it, because an early build once crashed a shared daemon and took my production services down for over a day. The same factory also runs non-software task types; the adventure generator in section 08 is one.

What works

  • The full loop from request to scored pull request, with specialist review panels
  • A seven-app suite (web UIs, REST APIs, a Go service and a Rust CLI) delivered as pull requests
  • Batches of API apps shipped unattended, end to end
  • A rule I hold: I never hand-fix an app Karakuri built. The fix goes into the factory, so the factory gets better.

What doesn’t yet

  • My bar is seven of ten fresh requests packaged at grade A, twice in a row. It isn’t reliably there yet. Most of the work now is the plumbing between agents, because that is where it loses context.
  • Complex apps in any language, with persistence, Docker and end-to-end tests, is the target. It has shipped web, API, Go and Rust work. The rest of that list is still ahead.

07 · Quality

QA & test tooling in progress

A test-generation pipeline built from separate stages that meet only at model-free contracts, plus the harness that tells me whether it works.

PythonPlaywrightChromaDBJSON-schema contractspytest

I have been a tester my whole career, so this is the system I am hardest on. The pipeline has five small services. Spec intake reads a spec or ticket, interrogates it for assumptions and gaps, asks clarifying questions, and normalises the acceptance criteria into BDD. Creating anything in a system of record needs a human’s approval. The test-case designer expands that into positive, negative and boundary cases. The synthesizer turns each step into automation: it reuses a proven step from the library when one matches, and otherwise derives the step by driving the live app (map it, walk the journey, adapt) and compiles the test from what it observed. The runner executes the test, heals locator drift, and on green promotes the new steps into the step library, which only ever holds steps that passed. A human merges the pull request.

Stages meet only at contracts: versioned JSON schemas with no model calls in them, so any stage can be swapped out or run alone. qa-eval is the harness that keeps me accurate. It runs the whole pipeline N times on every spec in a corpus and reports green rate, run-to-run consistency and why tests failed.

Self-healing is the part of this I am most careful with, because a test that quietly rewrites itself can hide a real bug. It lives in two places. Inside the pipeline, the runner repairs locator drift in a generated test, and when it can’t, it flags the test for a human and promotes nothing. Separately I keep two mirrored Playwright frameworks, Python and TypeScript, with self-healing locators and the Planner, Generator and Healer agent trio driven over MCP, plus a heal command that works with any OpenAI-compatible model, local or hosted. The rules come from what practitioners learned running this for real. Healing happens out of band: tests run and publish results first, and only afterwards does a separate step go back over the failures, never during the run and never automatically on a first failure. Each failure is reproduced in a real browser before anything is touched. The healer may change locators only, never assertions or what a test means. If a repair doesn’t hold, it is reverted and the failure is flagged as a likely app bug instead of being papered over, and everything lands as one pull request that lists each decision and the tests left alone for a human to review. I have run it end to end on a local 27-billion-parameter model: break a selector, watch it heal to a label-based locator, watch the test pass again. A nightly job now runs the end-to-end suite for one of my own services and calls the healer on whatever fails.

The result that changed the project: when the pipeline failed on basic demo apps, the model was not the bottleneck. A 27-billion-parameter local model, quantised to 4-bit, matched a frontier model on a controlled run (17 to 18 of 18 genuine passes) once the harness observed the real page and could address repeated elements. The earlier “small models hallucinate” results were harness bugs. Observation, not model size, was the fix. Alongside it are agent skills for generating test documents from specs and for coaching red-green-refactor, and a QA review panel inside Karakuri.

What works

  • Five stage services plus the shared contracts, each runnable alone
  • A step library that only ever learns from green runs, so it compounds
  • An eval harness that repeats the whole pipeline and reports consistency, not one lucky run
  • Derive-by-observation as the default synthesis mode
  • Out-of-band, locators-only healing: each failure is reproduced in a real browser, the fix is re-run to verify, and the result is one pull request, never a silent rewrite

What doesn’t yet

  • File and text specs work. Adapters for ticket trackers and wikis are stubs.
  • Validation so far is a corpus of small apps and specs. Scale is the next question, and I haven’t answered it yet.
  • Healing is proven on small demo apps and one of my own services, not on a large suite.
  • Grounded healing is designed, not built. When a locator is ambiguous the healer should check a requirements and ticket store, then ask a human, and a genuine app regression should raise a bug ticket. Today it reverts and flags.

08 · Games

AI game master in progress

Generate a tabletop adventure, then hand it to an LLM that runs it like a game master: you talk, it narrates, and the dice stay fair.

GoYAML rule adaptersWhisper (speech in)multi-voice TTS (speech out)generated ambience

It started as a Karakuri task type. The generator produces a complete module: scenes, boxed read-aloud text, skill checks, branching, NPCs, monsters, treasure and pregenerated characters, plus maps and handouts in four genres (fantasy, space, modern and western) and a vintage-style module booklet you can print. Maps cover regions, cities, dungeon interiors and star maps.

The runtime plays a module. The design splits three layers on purpose: content (what happens), a system adapter (how actions resolve), and the engine (the loop that plays it). The adapter is a config file, not code, so a new rule system is data and prompt, not a rewrite. And precision is an architecture property: all randomness goes through a deterministic dice engine. The LLM asks for a roll and consumes the result. It never invents one. Combat state (hit points, conditions, initiative) lives in code, turn order is enforced, and a player who tries to act out of turn is redirected instead of resolved.

On top of that the loop is voice-driven: speech-to-text takes what you say, a fast text-to-speech engine narrates with different voices for different characters, ambient beds and sound effects play, and the maps appear in the loop. A bake-off, not an assumption, chooses which model runs the table.

What works

  • Generator: modules, maps, handouts and booklets across four genres
  • A text play-loop proven end to end on a real module, saved and resumable
  • Voice in, multi-voice out, ambience, sound effects and maps in the loop
  • Turn-order enforcement, plus rules depth such as unconscious at zero hit points and advantage from conditions

What doesn’t yet

  • It is driven from a terminal. A proper player-facing table, a virtual tabletop, is the missing piece.
  • One rule system is fully wired in. More are drafted but not merged, and proving the adapter idea across several systems, including a non-fantasy one, is still ahead.

09 · Meetings

Meeting intelligence running

Recordings go in. Transcripts, speakers and summaries come out, and the work runs on my own machines.

FastAPIReactSQLitelocal ASR + diarizationvoiceprintsCPU-only

A self-hosted app, built on an open-source base I forked and then fixed where it fell short. Recordings arrive from handheld recorders and a phone app. A small watcher notices new audio files, sends them to the app, de-duplicates by hash, and sets the real recording date, which the app would otherwise stamp as “now”. Transcription, speaker diarization and voiceprint matching all run locally on the CPU. No GPU, by design, so it can live on a modest box. Summaries are written by a local model through the fleet proxy.

Speaker identification is the interesting part. The app keeps voiceprints and matches each speaker against the people who are enrolled. It can only name someone who is enrolled, and so far that is just me, so everyone else stays Speaker 1, Speaker 2. I would rather show “Speaker 2” than a confident wrong name.

What works

  • The whole pipeline end to end: capture, transcribe, diarize, identify, summarize
  • Automatic speaker matching on ingest for enrolled voices
  • A back catalog from a recorder’s archive re-transcribed locally

What doesn’t yet

  • It is still a trial deployment on a shared server, running on a capped slice of CPU, one meeting at a time. A dedicated old box is the plan.
  • Only enrolled voices get names. Enrolling more people needs clean per-person samples, and that isn’t done.

10 · Operations

Self-healing operations in progress

The goal is zero alerts. An alert means the automation gave up and handed the problem to me.

cron + launchd + systemdevent buslocal triage modelsIPMI watchdogsmart plugs

The rule I run the fleet by: for every recurring failure, prevent it and recover from it. Prevention means finding the real root cause, not a restart or a nag. Recovery means an autonomous fix, so that if it breaks anyway, no human has to be there. Two layers do most of the work. A mechanical monitor runs on a short cycle, checks the nodes and services, and fixes the failures it recognises: restart the agent, force a stuck git pull, bring a service back. Underneath that is hardware recovery: a watchdog that resets a hung machine, and smart plugs that let me power-cycle a box remotely.

Anything it can’t fix lands on an event bus, and a triage loop picks it up. A small local model reads the failure and diagnoses it. A bigger local model takes over only if the first is unsure. Triage is advisory: it never touches the fleet itself. If it recommends escalation, a fix runner can start a coding agent in a throwaway worktree with no push rights, and a human clicks Fix. Local models always go first. A frontier model is the last resort, never the first call.

Red Alert is the dispatcher: when self-healing fails, it sends an agent to investigate, with an escalation chain per issue type and a cooldown so one outage doesn’t spawn a swarm. An absence monitor watches for the quiet failures. It alerts on how stale an output is, not on whether a process is alive, and only on state changes, so a persistent failure doesn’t turn into hourly noise. The status page shows only what is down and says “all systems nominal” otherwise. Each machine also has its own runbook, and agents are required to read it before they touch that machine; a hook blocks them until they have.

The agent office is the one view that isn’t about failure. It’s a pixel-art office where every running agent session, the coding agents and the pipeline workers across my machines, shows up as a small character at a desk. Characters move between rooms depending on whether the agent is working, waiting or idle, so I can see at a glance what the whole fleet is doing. I built it because a list of sessions tells me little, and a stalled agent is easier to spot when it’s a character who hasn’t moved.

What works

  • A mechanical monitor, an event bus and two tiers of local-model triage
  • An absence monitor on intake, backups, memory indexing and telemetry
  • A status page that only shows trouble
  • A hardware watchdog on one big box and remote power control on others
  • Per-machine runbooks that agents are forced to read first

What doesn’t yet

  • Zero alerts is the north star, not the current state. Plenty of failures still end up as a message to me.
  • The last step is human on purpose: triage recommends, a person clicks Fix. Closing that loop safely is the open problem.
  • Success codes lie. Several checks reported healthy while doing nothing, including a backup job that had silently stopped for months, which is why monitors now measure output, not process state.
  • The monitors mostly run from one automation workstation. If it goes down, so does fleet-wide self-heal.

11 · Data

Storage & backup running

Hundreds of terabytes on shucked drives. The rule: if I can’t find it or reach it, I don’t really have it.

rsyncAES-256 (openssl)SSHcron + launchdUSB drive enclosures

Most of it is bulk on external drives in multi-bay enclosures. I sort the data by what losing it would mean. A slice is irreplaceable and gets real protection. The rest can be re-acquired and gets indexed and organised instead of blanket-backed-up. For the irreplaceable set, a nightly job mirrors every disk, one to one, to a backup server. It runs in an overnight window only, resumes where it left off, and refuses to write to a target that isn’t actually mounted, so a dropped drive can’t silently fill a boot disk.

State that exists nowhere else (agent memory, session history, configuration) gets a separate nightly encrypted backup: archived, compressed, encrypted with AES-256 and streamed over SSH to two destinations, with no plaintext archive ever on disk. Code isn’t in it, because git already replicates that to GitHub. Leaving out about a hundred gigabytes of repos is what makes the payload small enough to run every night.

I built this after a bad week. Something wiped two weeks of conversation history, and four systems that were supposed to prevent it were reporting healthy while doing nothing. Now an absence monitor checks the output: is the newest backup fresh, does a second copy exist, does the snapshot decrypt. A check that can’t tell reports failure, not silence.

What works

  • A nightly one-to-one mirror of the irreplaceable set to a backup server, with a mount guard
  • An encrypted nightly backup of state that exists nowhere else, to two destinations, with a verify mode that decrypts the newest snapshot
  • Backup freshness watched by an absence monitor

What doesn’t yet

  • macOS drops external disks on sleep and power events, and the file servers running it were unreliable and unindexed. The plan is Linux file servers that mount by UUID and pool with a union filesystem, no parity, on purpose. That rebuild is planned, not finished.
  • A set this big takes weeks of overnight windows to copy the first time. The mount guard exists because drives do drop.

The Bridge

A web page where I type a question, pick which agents and models take part, and watch them argue. Round one is opening arguments, streamed as they arrive. In round two each participant reads what the others said and rebuts. In round three one of them judges the whole exchange and says who made the best points. I can assign sides, for or against, so a model has to defend a position it wouldn’t pick. The panel can mix coding agents on different machines with local and hosted models, and anything offline is skipped.

It answers only on my home network, so there is no link. It is the quickest way I know to see models disagree.

3D modeling for print in progress

I model large scale-model kits for my own printer, with AI doing much of the geometry work. Everything is PLA, which is weak, so strength has to come from the design: thicker walls, fillets where a part meets its root, layers running along the load, a metal rod where a stress check fails, and pegs, magnets and glue instead of snap clips. The shape comes from the best source I have. If I’m given a 3D model, that model is the shape and my job is hollowing, splitting and adding play features. Otherwise it comes from orthographic drawings, which outrank photos. When code has to write the geometry, a local vision model does it one feature at a time: it renders its own work beside the drawing, compares, and fixes.

A model too big for the bed is split the way kit makers split them, and every seam gets a solid inner rim and alignment pins, never a bare glue line. Nothing reaches the slicer until two gates pass. A preflight script fails hard on loose bodies, overlapping parts, duplicates, missing magnet caps and any part out of position against the drawings. Then a render sheet puts the model next to the drawing, and I have to look at it before slicing is allowed. I added the gates after a build reached the slicer with overlapping parts and a part in the wrong place; the gate had to fail on that bad build before I trusted it. The current project is a large scale-model helicopter, built so a kid can assemble it with glue and drop-in magnets.

Spinn running

My coffee machine has one physical button, so most recipes need the maker’s phone app. A small open-source bridge I run at home gives it a web page instead, and the first cold brew with no app worked. I added two patches, one to ignore a harmless mid-brew grinder warning and one to show recipe pictures, and backed up the account’s recipes and images.

The catch is that it still talks through the maker’s own cloud. I tested pointing the machine at a local server instead, and it refused: the firmware checks the cloud’s certificate authority. The fallback is to swap the trusted certificate in the machine’s flash and run a small local broker. That is planned, not built.

herdr-web
A browser front end for herdr, a terminal workspace manager for coding agents. One hub reaches all twelve machines in the fleet over locked-down SSH keys and shows every agent session on every one of them in a single page, with each agent’s status. I can open any session’s live terminal and check on or steer it from my phone. Only I can get in: the page sits behind a single sign-in. The work lives in persistent terminal sessions on each machine, and the page only attaches to them.

Unwatched is a self-hosted town of AI citizens that I run from a fork of an open-source project. Each citizen is a language-model mind with its own memory, a plan for the day and an owner who can write to them but not give orders; they find work, talk to one another, buy and sell, and keep going on the real clock whether or not anyone is watching. I point the minds at local models on the fleet. The architecture I settled on is autonomous islands: each is a self-sufficient town in its own container, islands trade people and goods with one another peer to peer by boat, and an optional coordinator hub is designed on top but never required, so two islands and nothing else must work. It’s an experiment in long-running autonomous agents: I want to see what they do when nobody is steering them.
